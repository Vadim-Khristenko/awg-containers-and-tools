# AmneziaWG: контейнеры и инструменты

Свои собственные серверы AmneziaWG для **всех** поколений протокола — 1.0, 1.5, 2.0 и **3.0** — в виде небольших образов, плюс CLI на Rust, который генерирует параметры обфускации и умеет разворачивать сервер на удалённой машине по SSH.

**English version: [README.md](README.md)**

> **Неофициальный проект.** Это community-разработка. Она никак не связана с AmneziaVPN, не одобрена и не поддерживается ими. Если что-то здесь сломалось — заводите issue **в этом репозитории**, пожалуйста, не пишите об этом в апстрим.

---

## Зачем это нужно

AmneziaWG 3.0 вышел уже давно, и клиенты его поддерживают. А вот поднять свой сервер — отдельная история.

Официальный путь настройки идёт через `awg-quick`: он читает `.conf` и скармливает его `awg setconf`. Этот парсер живёт в `amneziawg-tools`, и он до сих пор понимает только набор ключей от 2.0. Дайте ему конфиг 3.0 — он споткнётся на первой же незнакомой строке:

```
$ awg setconf awg0 awg0.conf
Line unrecognized: `HeaderProtectionKey=...'
Configuration parsing error
```

При этом сам демон в полном порядке — `amneziawg-go` v3.0.2 реализует 3.0 целиком. Отстал только слой конфигурации перед ним. Поэтому проект этот слой обходит и разговаривает с демоном напрямую через UAPI-сокет, который принимает все ключи 3.0 уже сегодня.

Вот и весь фокус. Всё остальное — это упаковка, генерация параметров и попытка сделать так, чтобы этим было приятно пользоваться.

### Как оно таким получилось

Начиналось всё как небольшая утилита, чтобы ставить AmneziaWG было не так муторно, — обёртка вокруг шагов, которые и так делали руками. Потом выяснилось, что self-hosted 3.0 нет вообще ни у кого, ну а живём один раз. Так оно и выросло в оператора собственного хозяйства: собирает образы, ставит их на сервер, выдаёт клиентские конфиги и говорит, если с результатом что-то не так.

Рано или поздно официальный self-hosted 3.0 появится в апстриме. Появится — пользуйтесь им. А пока работает это.

Все четыре спокойно работают на одном хосте одновременно и не мешают друг другу.

## Быстрый старт

### Поднять сервер 3.0 через Docker Compose

```bash
git clone https://github.com/Vadim-Khristenko/awg-containers-and-tools
cd awg-containers-and-tools/containers
```

Сгенерируйте один блок параметров и вставьте его в **оба** файла — `server.conf` и `client.conf`. Параметры обфускации обязаны совпадать на двух концах, иначе пиры просто не узнают пакеты друг друга:

```bash
awg-tool gen --version 3.0 --lang ru
```

Добавьте ключи и адреса, а дальше:

```bash
docker compose up -d
docker compose exec server awg-uapi get      # хендшейки, счётчики трафика
docker compose exec server awg-peer add laptop
```

`awg-peer add` печатает готовый клиентский конфиг, который можно сразу импортировать.

### Поставить на удалённый сервер по SSH

```bash
awg-tool install --host 203.0.113.9 --user root --key ~/.ssh/id_ed25519
```

Сначала он смотрит на машину и только потом что-то меняет: какой дистрибутив, работает ли docker и нужен ли ему `sudo`, какой адрес показывать клиентам. Он знает двенадцать самых распространённых дистрибутивов и умеет откатываться по `ID_LIKE` для производных, так что Zorin считается Ubuntu, а CachyOS — Arch.

Если пакета не хватает — печатает точную команду и спрашивает разрешения. На NixOS останавливается и выдаёт кусок для `configuration.nix`, потому что императивная установка пакетов там не переживёт следующий ребилд.

Если на порту туннеля уже кто-то слушает — говорит, кто именно, и останавливается. Чужой процесс он не убьёт: выбрать свободный порт через `--listen-port` стоит одного флага, а убить не тот процесс — целого сервера.

В конце печатает клиентский `.conf` и ссылку `vpn://`.

Осмотр не делает исходящих запросов **с вашего сервера**: адрес берётся из источника маршрута по умолчанию, а не с внешнего echo-сервиса. И `sudo docker info` пробуется только если обычный вызов уже не прошёл — лишний `sudo` на чужой машине поднимает тревогу в аудите на ровном месте.

Профили подключения сохраняются, так что второй запуск — это `--server ИМЯ`. Пароль попадает на диск, только если вы сами об этом попросите.

### Управлять тем, что уже стоит

```bash
awg-tool status --server home     # что запущено, пиры, хендшейки, трафик
awg-tool doctor                   # почему оно не везёт трафик
awg-tool logs --lines 200         # журнал, из которого вырезан ключевой материал
awg-tool update                   # не устарел ли инструмент или образ
```

`status` находит наши контейнеры по ссылке на образ, поэтому переименованный узел всё равно найдётся, а чужой контейнер никто не тронет.

`doctor` возвращает вердикт с уровнем уверенности, доказательствами и следующим шагом, а не простыню логов. Он различает отсутствующий `/dev/net/tun`, отсутствующий `NET_ADMIN`, выключенный `ip_forward` и пира, который просто ни разу не выходил на связь. А когда доказательств не хватает, чтобы отделить одну причину от другой, он так и говорит и перечисляет обе, вместо того чтобы выбрать более вероятную.

`logs` вычищает секреты на выходе из библиотеки, а не в месте печати: приватные ключи, pre-shared-ключи и ключи защиты заголовков эту границу не пересекают, поэтому вывод можно куда-то вставить.

### Просто сгенерировать конфиг

```bash
awg-tool gen --version 3.0 --profile quic --client amneziavpn
awg-tool gen --version 2.0 --client amneziawg-windows --browser chrome
awg-tool gen --version 3.0 --uapi          # строки UAPI вместо .conf
```

## Генерация параметров

Каждый запуск даёт новый набор параметров. Это важнее, чем кажется: если бы все разворачивали одни и те же числа, любой сервер, собранный этим инструментом, имел бы один и тот же DPI-отпечаток — и заблокировать их все разом было бы делом одной сигнатуры. Рандомизация на каждую установку — это и есть смысл.

Генератор следит за настоящими ограничениями протокола, а не просто выдаёт правдоподобные числа: нижняя граница S при включённой защите заголовков, соотношение таймеров rekey и reject, свой словарь тегов для каждой версии и потолки размеров, которые удерживают мусорные пакеты внутри вашего MTU.

### Профили мимикрии

Мусорные пакеты `I1`–`I5` можно замаскировать под обычный трафик:

```
quic  quic0rtt  tls  noise  dtls  http3  sip  tls-to-quic  quic-burst  dns  random
```

```bash
awg-tool profiles          # посмотреть список
awg-tool gen --profile tls --host cdn.example.com
```

Ключ `--browser chrome|edge|firefox|safari|yandex-desktop|yandex-mobile` подгоняет размеры под то, что реально отправляет соответствующий браузер, вместо размеров, которых ни один браузер никогда не выдаст.

### Ограничения клиентов

Клиенты принимают разное, и конфиг, вылезший за чей-то предел, отваливается при импорте — иногда с ошибкой, иногда молча. Флаг `--client` подрезает вывод под то, что ваш клиент действительно умеет:

```bash
awg-tool clients
```

| Клиент | Что важно знать |
|---|---|
| AmneziaVPN | поддерживает всё |
| AmneziaWG Android / iOS | поддерживают всё |
| AmneziaWG Windows | H-значения ограничены `INT32_MAX` |
| WG Tunnel | большие S3/S4 сажают батарею — держите S4 скромным |
| WireSock | нет тегов `<c>`/`<rc>`/`<rd>` |
| Keenetic (native) | чувствителен к сложному `I1`; лучше простой мусор или DNS-мимикрия |
| amneziawg-go (legacy) | `<c>` не реализован — выдаёт ErrorCode 1000 |
| OpenWRT, ASUS Merlin | поддерживают всё |

Именно поэтому тег `<c>` **по умолчанию выключен**. Флаг `--tag-c` включает его, если вы уверены в своём клиенте.

### Форматы экспорта

Оба формата, которые использует экосистема Amnezia:

- `.conf` — обычный файл в стиле WireGuard
- `vpn://` — однострочная ссылка, которую клиент Amnezia импортирует напрямую

## Защита от утечки DNS

Резолвер стоит на отдельной bridge-сети по адресу `172.29.172.254` — ровно так же, как это сделано в самом AmneziaVPN. Его порт никуда не опубликован, и до этой сети не дотягивается ничто другое, поэтому клиент с `DNS = 172.29.172.254` может получить ответ только через туннель.

Это гарантия посильнее, чем «резолвер приоритетнее». Запрос, утёкший мимо туннеля, не уйдёт тихонько к резолверу провайдера — он не дойдёт вообще никуда и сломается заметно.

## Управление сервером

Когда сервер уже поднят:

```bash
awg-peer add <метка> [ip]        # новый пир; печатает конфиг клиента один раз
awg-peer list                    # метка, публичный ключ, адрес, последний хендшейк
awg-peer rm <метка|pubkey>       # отозвать
awg-uapi get                     # сырое состояние демона
```

Приватный ключ нового пира генерируется внутри контейнера, печатается один раз и на диск не попадает. Хранятся метка, публичный ключ, адрес и pre-shared-ключ — последний потому, что серверу он снова нужен после каждого перезапуска.

Ещё узел ведёт журнал событий в `/var/log/awg/events.log`, дублируя его в `docker logs`: когда узел поднялся, когда настроили интерфейс, кому выдали доступ и когда его забрали. Приватных ключей, pre-shared-ключей и тел конфигов там нет — публичного ключа вполне достаточно, чтобы опознать пира. Но журнал всё равно чувствительный, потому что он и есть список тех, у кого есть доступ, так что обращайтесь с ним соответственно и не вставляйте его в issue. Размер ограничен по построению: 256 КиБ плюс одна ротация, так что узел, который дёргается весь год, всё равно стоит полмегабайта.

## Сборка из исходников

Нужен Rust 1.90 или новее (edition 2024):

```bash
cargo build --release
./target/release/awg-tool --help
```

Собрать образы самому:

```bash
cd containers
./build.sh
./selftest.sh        # поднимает живой туннель для каждого поколения и доказывает, что трафик идёт
```

`selftest.sh` — это не проверка «а оно запустилось»: он устанавливает хендшейк, прогоняет данные и сверяет контрольные суммы на той стороне, и так для каждого из четырёх поколений.

## Статус

Работает сейчас: генерация параметров для всех четырёх версий, интерактивный интерфейс, все пять образов, развёртывание по SSH, поиск контейнеров, состояние, диагностика, очищенные журналы, проверка обновлений и оба формата экспорта.

В планах: веб-интерфейс, сборки под WASM, сборки под Android.

Это релиз `0.2.2`. Тестов — 326, контейнеры проверяются живыми туннелями, а не «оно запустилось», а `install` прогоняется целиком против одноразовой виртуалки. Но инструмент молодой, так что рассказывайте, что сломалось.

### Проверить скачанное

В каждом релизе лежит файл контрольных сумм, названный по тегу:

```bash
sha256sum -c checksums-v0.2.2.sha256
```

Бинарники не подписаны. Контрольная сумма говорит, что файл дошёл целым, но не говорит, кто его собрал.

Ограничения, чтобы не были сюрпризом:

- Интерфейс подключается к профилям, которым пароль не нужен, либо чей пароль вы сами решили сохранить. Всё остальное — одна команда, и экран об этом прямо говорит.
- Если порт туннеля занят, инструмент скажет, кем именно, и остановится. Убивать за вас он не станет.
