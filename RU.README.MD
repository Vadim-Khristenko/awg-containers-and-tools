# AmneziaWG Containers and Tools

Самостоятельно размещаемые серверы AmneziaWG для **каждого** поколения протокола (1.0, 1.5, 2.0, **3.0** и **3.1**) в виде небольших образов, резолвер, доступный только из туннеля, со своими страницами в зоне `.vpn`, и CLI на Rust с интерактивным интерфейсом: генерирует параметры обфускации, ставит серверы по SSH и потом ими управляет.

**English version: [README.md](README.md)**

> **Неофициальный проект.** Это проект сообщества. Он не связан с AmneziaVPN, не одобрен и не поддерживается ею. Если что-то сломалось, заводите issue **в этом репозитории**, пожалуйста, а не в upstream.

---

## Зачем это

AmneziaWG 3.0 вышел давно, и клиенты его поддерживают. А вот поднять его у себя было отдельной историей.

Официальный серверный путь настраивает туннель через `awg-quick`: тот читает `.conf` и передаёт его в `awg setconf`. Этот парсер живёт в `amneziawg-tools` и долгое время понимал только ключи 2.0. На конфиге 3.0 он останавливался на первой незнакомой строке:

```
$ awg setconf awg0 awg0.conf
Line unrecognized: `HeaderProtectionKey=...'
Configuration parsing error
```

Сам демон был в порядке: `amneziawg-go` полностью реализует 3.0 (а теперь и 3.1). Отставал только путь конфигурации перед ним. Поэтому проект этот путь обходит и говорит с демоном напрямую через его UAPI-сокет: один формат запроса на все версии от 1.0 до 3.1, который не зависит от того, что умеют парсить утилиты в образе.

Вот и весь фокус. Всё остальное здесь упаковка, генерация параметров и забота о том, чтобы этим было приятно пользоваться.

### Как так вышло

Начиналось с мелочи: сделать установку AmneziaWG менее нудной, обёртка вокруг шагов, которые люди и так делали руками. Потом выяснилось, что поднять у себя 3.0 не может вообще никто, а живём один раз. Так проект вырос в оператора собственного стека: собирает образы, ставит их на сервер, выдаёт клиентские конфиги, по просьбе меняет обфускацию и говорит, когда с результатом что-то не так.

Официальный self-hosted 3.0 рано или поздно появится в upstream. Когда появится, пользуйтесь им. А пока работает это.

## Быстрый старт

### Сервер через Docker Compose

```bash
git clone https://github.com/Vadim-Khristenko/awg-containers-and-tools
cd awg-containers-and-tools/containers
```

Сгенерируйте один блок параметров и вставьте его **в оба** файла, `server.conf` и `client.conf`. Параметры обфускации должны совпадать на обоих концах, иначе пиры не узнают пакеты друг друга:

```bash
awg-tool gen --version 3.1
```

Добавьте ключи и адреса, затем:

```bash
docker compose up -d
docker compose exec server awg-uapi get      # рукопожатия, счётчики трафика
docker compose exec server awg-peer add laptop
```

`awg-peer add` печатает готовый клиентский конфиг. Compose заодно поднимает резолвер и страницы вместе с общими томами: имена пиров узла (для `<метка>.peer.vpn`), собственные списки резолвера и счётчики, которые показывает `dns.vpn`.

### Установка на удалённый сервер по SSH

```bash
awg-tool install --host 203.0.113.9 --user root --key ~/.ssh/id_ed25519
```

Прежде чем что-то менять, он смотрит на машину: какой дистрибутив, работает ли docker и нужен ли ему `sudo`, на какой адрес направлять клиентов. Знает двенадцать самых частых дистрибутивов и для производных идёт по `ID_LIKE`, так что Zorin считается Ubuntu, а CachyOS считается Arch.

Если не хватает пакета, он печатает точную команду и спрашивает, прежде чем её выполнить. На NixOS он останавливается и выдаёт кусок `configuration.nix`: императивная установка пакетов там не переживёт следующую пересборку.

Если порт туннеля уже кто-то слушает, он скажет кто и остановится. Чужой процесс он за вас не убьёт: выбрать свободный порт через `--listen-port` стоит одного флага, а убить не то стоит сервера.

В конце вы получите клиентский `.conf` и ссылку `vpn://`. Все параметры `gen` работают и здесь; имя, которое имитирует мимикрия, здесь задаётся через `--mimic-host`, потому что `--host` это сервер.

Обследование не делает исходящих соединений *с* вашего сервера: адрес для клиентов берётся из источника маршрута по умолчанию, а не у внешнего echo-сервиса. А `sudo docker info` пробуется, только если обычный вызов уже не сработал: лишний `sudo` это способ поднять тревогу аудита на чужой машине.

Профили подключений сохраняются, так что второй запуск это `--server ИМЯ`. Пароли попадают на диск, только если вы сами об этом попросите. Ключ хоста никогда не принимается молча: при первом подключении показывается отпечаток и задаётся вопрос, а сменившийся ключ останавливает всё.

### Откуда взять бинарник

Начиная с `0.3.0` к каждому релизу прикладываются бинарники: `awg-tool-linux-amd64`, `awg-tool-linux-arm64`, сборки для Windows и macOS и контрольные суммы. Если хотите собрать сами:

```bash
cargo build --release            # нужен Rust 1.90+, edition 2024
./target/release/awg-tool --help
```

или запустить без установки:

```bash
cargo run -p awg-cli -- gen --version 3.1
```

## Работа с тем, что уже стоит

```bash
awg-tool status --server home     # что запущено, пиры, рукопожатия, трафик
awg-tool status --local           # контейнеры на этой машине, без SSH
awg-tool doctor                   # почему не идёт трафик?
awg-tool logs --lines 200         # журнал без ключей
awg-tool update                   # не устарели ли утилита или образ?
```

`status` находит наши контейнеры по образу, а если образ переименовали, то по метке, которую несут образы. Так что переименованный узел всё равно найдётся, а чужой контейнер останется нетронутым. Если не указаны ни `--server`, ни `--host`, а на этой машине уже работают наши контейнеры, ответ идёт отсюда, без вопроса, какой сервер имелся в виду. `--local` делает это принудительно; `--container ИМЯ` (или `auto`) выбирает один узел, когда их несколько.

`doctor` выдаёт вердикт с уровнем уверенности, доказательствами и следующим шагом, а не стену логов. Он отличает отсутствие `/dev/net/tun` от отсутствия `NET_ADMIN`, выключенный `ip_forward` от пира, который просто ни разу не рукопожимался, и когда по доказательствам две причины не различить, так и говорит и перечисляет обе.

`logs` вычищает ключи на выходе из библиотеки, а не перед печатью: приватные ключи, pre-shared ключи и ключи защиты заголовков эту границу не пересекают, так что вывод можно смело куда-то вставлять.

### Пиры

```bash
awg-tool peer add phone                  # новый пир; конфиг печатается один раз
awg-tool peer add phone --vpn --mihomo   # ...плюс ссылка vpn:// и блок для mihomo
awg-tool peer add phone --out phone.conf # в файл, доступный только владельцу
awg-tool peer list                       # метка, публичный ключ, адрес, последнее рукопожатие
awg-tool peer rm phone                   # отозвать, по метке или публичному ключу
```

Всё это работает и здесь, и по SSH, как `status`. Выданный конфиг проверяется до печати, так что узел, у которого разъехался собственный конфиг, скажет об этом сразу, а не клиентом, который так и не подключится.

### Новая обфускация для работающего узла

```bash
awg-tool rotate --dry-run         # что поменяется и кому понадобится новый блок
awg-tool rotate                   # спросит и сделает
awg-tool rotate --out block.conf  # новый блок для клиентов в файл
```

Ротация заменяет всё, о чём договариваются оба конца (мусор, размеры, заголовки, цепочки, ключи 3.x), и не трогает собственное сервера: ключ, адрес, порт и пиров. Конфиг читается через контейнер, по монтированию находится файл на хосте, рядом кладётся резервная копия, узел перезапускается и ожидается, а если не поднялся, старый конфиг возвращается. После этого всем клиентам нужен новый блок, поэтому это осознанное действие, а не настройка.

По SSH приватный ключ сервера и pre-shared ключи его пиров никуда не передаются, даже внутри командной строки, которую на сервере показал бы `ps`: отправляется только новый блок, переписывание происходит рядом с файлом, и то, что затем читает контейнер, должно байт в байт совпасть с запланированным конфигом, иначе возвращается копия.

### Интерфейс

`awg-tool` без аргументов открывает его. Всё перечисленное выше есть и там: генератор со всеми ручками и сохранёнными наборами, экран проверки и экран серверов, где первой строкой идёт docker этой машины, а ниже сохранённые подключения. На узле: `p` пиры, `+` выдать, `-` отозвать, `R` сменить обфускацию (сначала показывается, потом подтверждается вводом имени узла), `d` диагностика, `L` журнал. На резолвере: `b`/`B` заблокировать и снять блок, `a`/`A` разрешить и снять разрешение, `/` спросить имя.

## Генерация параметров

```bash
awg-tool gen --version 3.1 --client amneziavpn
awg-tool gen --version 3.0 --profile quic --region ru --whitelisted ru
awg-tool gen --version 2.0 --client amneziawg-windows --client-release pre-2.0.2
awg-tool gen --version 3.1 --uapi              # строки UAPI вместо .conf
awg-tool gen --version 3.1 --mihomo            # блок прокси для mihomo (Clash.Meta)
awg-tool gen --version 3.1 --json              # для скриптов
awg-tool gen --version 3.1 --save phone        # сохранить настройки как набор
awg-tool gen --set phone                       # и применить снова
```

Каждый запуск даёт свежий набор параметров. Это важнее, чем кажется: если бы все разворачивали одни и те же числа, у всех серверов, собранных этим инструментом, был бы один отпечаток для DPI, и заблокировать их все разом было бы тривиально.

Генератор соблюдает настоящие ограничения протокола, а не выдаёт правдоподобные числа: потолки S, при которых каждое сообщение влезает в MTU, нижнюю границу S при защите заголовков, связь таймеров rekey и reject, совпадения размеров, которые отвергает каждое поколение демона, словарь тегов движка на каждом конце и бюджет netlink модуля ядра в 3200 байт.

Выбор версии применяет её пресет, как это делает Any Tech ARCHITECT. Для 3.1 это MTU 1280, включённый `RandomTrailers` и H1-H4 как 1, 2, 3, 4; `DisableCookies` остаётся выключенным, потому что ломает keepalive за NAT под нагрузкой. Каждый переключатель принимает `on` или `off`: `--random-trailers off`, `--disable-h off`, `--header-protection`, `--content-padding`, `--random-timings`, `--same-s`. Полный список в `awg-tool --help`.

### Профили мимикрии

Пакеты `I1`-`I5` можно оформить под обычный трафик:

```
quic  quic0rtt  tls  noise  dtls12  dtls13  http3  sip  tls-to-quic  quic-burst  dns  stun  random
```

```bash
awg-tool profiles                      # список
awg-tool hosts --role quic --region ru # имена хостов, которые они могут называть
awg-tool gen --profile tls --host cdn.example.com
```

Имена берутся из базы примерно в 2400 хостов по ролям и регионам, так что QUIC-пакет называет хост, который действительно говорит на QUIC и правдоподобен там, где вы находитесь; `--whitelisted ru` оставляет только хосты, которые работают и при ограничениях сети. `--browser` подгоняет размеры пакетов под настоящий браузер (chrome, edge, firefox, safari, ios, yandex-desktop, yandex-mobile, 360, qq).

### Клиенты

```bash
awg-tool clients
```

Клиенты принимают не одно и то же, и конфиг, выходящий за чьё-то ограничение, ломается при импорте, иногда громко, иногда нет. `--client` урезает вывод под ваш клиент, `--client-release` под его старую сборку, а `--server-engine` под то, что разбирает цепочки на сервере. Тег `<c>` используется только там, где его понимают оба движка: у amneziawg-go нет счётчика пакетов, он есть только в модуле ядра Linux.

### Проверка чужого конфига

```bash
awg-tool check client.conf
awg-tool check 'vpn://...' --client amneziawg-windows
awg-tool check - --json < server.conf
```

Код 0 если всё чисто, 1 при предупреждениях, 2 при ошибках, так что скрипт может на это опираться. Замечания выводятся по-английски или по-русски (`--lang ru`).

## DNS

Резолвер живёт в собственной bridge-сети на `172.29.172.254`, как это делает AmneziaVPN. Его порт никуда не опубликован, и никакая другая сеть до этого моста не достаёт, так что клиент с `DNS = 172.29.172.254` может получить ответ только через туннель. Запрос, утёкший мимо туннеля, не уходит тихо к резолверу провайдера: он не доходит никуда и падает заметно.

Он резолвит сам от корня, если корень отвечает из вашей сети, и по DoT через Cloudflare и Quad9, если нет (`AWG_DNS_MODE=auto` по умолчанию; `recursive` и `forward` фиксируют одно). DNSSEC проверяется.

### Списки, записи и зоны

Всё, что вы меняете, лежит в одной папке, монтируемой в `/etc/awg-dns`; всё необязательно и подхватывается без перезапуска:

```
blocklists.d/*.txt     что блокировать: просто имена, строки hosts или adblock `||name^`
blocklists.url         адреса списков, по одному в строке, обновляются раз в сутки
allowlist.d/*.txt      имена, которые не блокируются, что бы ни говорил список
records.d/*.records    свои записи: `nas.home A 192.168.1.10`
vpn.d/*.records        имена в собственной зоне туннеля .vpn
forward.d/*.conf       зоны, отправляемые выбранным резолверам: `home.arpa. 192.168.1.1`
chain.conf             резолверы, которых спрашивают по порядку (ниже)
```

Из CLI, на том хосте, который выбрал бы `status`:

```bash
awg-tool dns                      # режим, счётчики, зоны, цепочка, доля кэша
awg-tool dns block ads.example    # и всё под ним
awg-tool dns allow www.example    # сквозь заблокированного родителя
awg-tool dns query example.com    # что ответит резолвер
```

Заблокированное имя получает NXDOMAIN от самого резолвера. Файл с плохой строкой резолвер не уронит: каждый сгенерированный конфиг проверяется до применения, а сломанный откатывается к последнему рабочему. Ещё резолвер отвечает на канарейку DoH из Firefox (а с `AWG_DNS_CANARY="firefox icloud"` и на iCloud Private Relay), чтобы браузеры держались его, а не резолвили в обход.

### Цепочка: другие корни, фильтры и запасные резолверы

`chain.conf` перечисляет резолверы в том порядке, в каком их спрашивают; `default` это собственный способ резолва этого резолвера:

```
default
185.121.177.177     # OpenNIC
```

С цепочкой всё резолвится как раньше, а имя, которого по словам настоящего корня не существует (например, `.geek`), спрашивается дальше по цепочке. Цепочка переходит к следующему резолверу, если ответа нет вовремя, пришёл SERVFAIL, REFUSED, NXDOMAIN или ответ, указывающий только на `0.0.0.0`, `127.0.0.0/8`, `::` или `::1`: так большинство фильтрующих резолверов говорят «заблокировано». Поставьте фильтрующий резолвер первым, и заблокированное им ответит следующий; поставьте первым `default`, и остальные ответят на то, чего нет у настоящего корня.

Молчащий резолвер не ждут до конца: через 400 мс рядом с ним спрашивают следующий, а у более раннего ещё ненадолго остаётся приоритет, так что медленный, но правильный ответ всё равно побеждает. Ответ засчитывается, только если пришёл с того адреса, который спрашивали, с id и вопросом запроса. `AWG_DNS_CHAIN_SINKHOLES` добавляет адреса, означающие «заблокировано», `AWG_DNS_CHAIN_KEEP` принимает причину вместо перехода дальше, а `AWG_DNS_CHAIN` задаёт цепочку без файла. Цепочка включается, меняется и выключается вместе с файлом, без перезапуска.

Для одной зоны проще `forward.d`: `geek. 185.121.177.177` отправляет в OpenNIC эту зону и только её. Это работает и для зон, на которые unbound по умолчанию отвечает сам, вроде `home.arpa.` или частной обратной зоны, так что имена домашней сети может отдавать роутер.

### Страницы туннеля

Compose поднимает контейнер страниц, который отвечает на несколько имён в зоне `.vpn`:

| | |
|---|---|
| `amiunder.vpn` | вы под VPN? Если страница открылась, да: `.vpn` не настоящий домен верхнего уровня, а адрес отвечает только внутри туннеля |
| `dns.vpn` | режим резолвера, его счётчики, счётчики цепочки и поле, чтобы спросить имя |
| `speed.vpn` | задержка, загрузка и отдача через туннель, до этого узла и обратно |
| `mtu.vpn` | проходят ли большие пакеты, от 1 КБ до 1 МБ в обе стороны |
| `leak.vpn` | резолвит ли браузер через туннель или в обход (чаще всего через DoH) |
| `node.vpn` | протокол, демон и MTU узла и все страницы выше |

Если открыть по адресу, а не по имени, страница выбирается фрагментом (`http://172.29.172.253/#dns`). Всё на страницах берётся с того же хоста: никаких сторонних спидтестов, счётчиков и запросов, которые могли бы выдать ваш реальный адрес. Страницы показывают только количества, никогда не имя, которое кто-то спрашивал, и никогда имена других пиров. Они говорят по-русски и по-английски, а стили это сам Architect kit, отдаваемый локально.

## Внутри узла

```bash
awg-peer add <метка> [ip]        # новый пир; клиентский конфиг печатается один раз
awg-peer list                    # метка, публичный ключ, адрес, последнее рукопожатие
awg-peer rm <метка|ключ>         # отозвать
awg-uapi get                     # сырое состояние демона
```

Приватный ключ нового пира генерируется внутри контейнера, печатается один раз и на диск не попадает. Хранятся метка, публичный ключ, адрес и pre-shared ключ, последний потому, что он нужен серверу после каждого перезапуска.

Узел ведёт журнал событий в `/var/log/awg/events.log`, продублированный в `docker logs`: когда поднялся, когда настроен интерфейс, кому выдан доступ и когда отозван, какие пиры замолчали и вернулись. Приватных ключей, pre-shared ключей и тел конфигов там нет. Он всё равно чувствительный, потому что это и *есть* список тех, у кого есть доступ. Размер ограничен 256 КиБ плюс одна ротация.

### Когда не работает

В каждом образе узла есть утилиты как раз на этот случай:

```bash
awg-health                 # код 0, когда узел может нести трафик
awg-under                  # «я под VPN?» изнутри клиентского узла
awg-leak                   # утечки DNS, IPv6 и маршрутов изнутри клиентского узла
awg-mtu                    # самый большой пакет, который реально проходит через туннель
awg-watch                  # пиры: активен, замолчал или ни разу не подключался
awg-dump > dump.txt        # вся картина, чтобы вставить куда нужно
```

`awg-leak` спрашивает `resolver.vpn`, а не верит любому ответу: в сетях, которые сами отвечают на DNS к любому адресу, адрес резолвера туннеля отвечает даже без туннеля, и только настоящий знает своё имя. Ещё он ловит IPv6-маршрут по умолчанию мимо полного IPv4-туннеля, самую частую утечку скопированного конфига.

`awg-mtu` находит самый большой размер, на который приходит ответ через туннель, и если он меньше MTU интерфейса, говорит, что поставить в конфиг. `awg-watch` по умолчанию работает в каждом узле (`AWG_WATCH=off` его выключает) и пишет `peer-quiet` и `peer-back`, когда пиры перестают и снова начинают рукопожиматься.

С самой клиентской машины:

```bash
awg-tool under             # спрашивает резолвер туннеля и страницу, код 0 под VPN
awg-tool under --json
```

## Сборка из исходников

Rust 1.90 или новее (edition 2024):

```bash
cargo build --release
./target/release/awg-tool --help
```

Сборка образов и проверка на живых туннелях:

```bash
cd containers
./build.sh
./selftest.sh 3.1     # настоящий туннель, данные через него, контрольные суммы на той стороне
./dnstest.sh 3.1      # резолвер изнутри и снаружи туннеля, страницы, цепочка
./utiltest.sh 3.1     # утилиты узла, включая случаи, где они обязаны сказать «нет»
```

Это не smoke-тесты. Один `dnstest.sh` доказывает, что резолвер недоступен снаружи туннеля, проверяет списки, свои записи, страницы и их CGI, `awg-mtu` на искусственной чёрной дыре, `awg-watch` на клиенте, который уходит и возвращается, и цепочку, которую включают, переставляют и выключают на работающем резолвере.

В планах: веб-интерфейс, сборки WASM, сборки для Android.

### Проверка скачанного

К каждому релизу прикладывается файл контрольных сумм с именем по тегу:

```bash
sha256sum -c checksums-v0.5.0.sha256
```

Бинарники не подписаны. Контрольная сумма говорит, что файл дошёл целым, но не говорит, кто его собрал.

Известные ограничения, чтобы не было сюрпризов:

- Интерфейс подключается к сохранённым профилям, которым не нужен пароль или пароль которых вы решили сохранить. Всё остальное делается одной командой, и экран об этом говорит.
- Если порт туннеля занят, утилита скажет кем и остановится. За вас она его не освободит.
- Ответы резолверов дальше по цепочке не проходят проверку DNSSEC: другой корень не пройдёт валидатор, который доверяет только корню ICANN.
