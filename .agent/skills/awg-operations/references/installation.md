## Выбор пути и требования

| Нужно | Подход |
|---|---|
| Только параметры обфускации | `awg-tool gen`; Docker и SSH не нужны |
| Проверить чужой `.conf` или `vpn://` | `awg-tool check`; ничего не меняет |
| Новый удалённый сервер любого поколения с первым клиентом | `awg-tool install` по SSH, с ограничениями ниже |
| Внутренний DNS, страницы .vpn, своя подсеть, управляемый Compose | Ручной контейнерный путь |
| Ещё одно устройство на уже работающем сервере | [clients.md](clients.md), не повторная установка |
| Только понять состояние | [operations.md](operations.md), без переустановки |

Контейнерному серверу нужны Linux-хост с Docker, `/dev/net/tun`, `NET_ADMIN`,
IPv4 forwarding, доступный клиентам **UDP**-порт и отсутствие пересечения
туннельных и bridge-подсетей с существующими сетями. Для Compose нужен плагин
`docker compose`. Rootless Docker, ограниченный VPS/LXC и отсутствие TUN не
считай заранее поддержанными: сначала проверь возможности хоста.

Не разворачивай VPN на машине разработки только для проверки документации.
Выполнение на рабочем сервере требует явного выбора хоста и согласования
системных изменений. Не отключай firewall целиком; правило на UDP-порт и
cloud security group/NAT проверяются отдельно, без риска потери SSH-доступа.

## Получение awg-tool

Для опубликованного релиза выбери бинарник под платформу на странице Releases
**этого** репозитория (`awg-tool-linux-amd64`, `awg-tool-linux-arm64`, сборки
для Windows и macOS). Скачай checksum-файл, проверь SHA-256, затем разреши
исполнение и установи бинарник в каталог из PATH. Не угадывай URL и номер
последнего релиза. Пример проверки:

```bash
sha256sum -c checksums-v0.5.0.sha256
```

Checksum проверяет целостность скачанного файла, не авторство: бинарники не
подписаны. Если checksum перечисляет несколько файлов, проверь строку
выбранного артефакта; отсутствие других файлов не подтверждает выбранный.

Из исходников, из корня checkout:

```bash
cargo build --release -p awg-cli --locked
./target/release/awg-tool --help
```

Нужны Rust 1.90+ (edition 2024), нативный компилятор и инструменты сборки
зависимостей. OpenSSL собирается vendored, системный OpenSSL не требуется,
и SSH на всех платформах идёт через этот OpenSSL. Для Windows/MSVC нужны
MSVC environment и нативный Strawberry Perl раньше MSYS2/Cygwin Perl в PATH.
Docker не нужен для сборки CLI и генерации.

Без установки бинарника в PATH:

```bash
cargo run -p awg-cli -- gen --version 3.1
cargo run -p awg-cli -- clients
```

Запуск без аргументов открывает интерфейс, только если stdin и stdout это
терминалы; иначе печатается справка. Общая справка: `awg-tool --help` или
`awg-tool help`. `--version` это версия протокола для генерации, не способ
узнать версию бинарника (её печатает первая строка `--help`).
Флаги пиши после команды и раздельно: `--flag VALUE`, не `--flag=VALUE`.

## Новый сервер по SSH

### Предварительные решения

Уточни SSH host/port/user, способ входа (agent, ключ, пароль), необходимость
sudo, публичный адрес для endpoint, свободный UDP-порт и поколение протокола.
`--host` это SSH-адрес; `--endpoint` это адрес **для VPN-клиентов**, они могут
отличаться. За NAT endpoint не получится достоверно вывести из частного адреса
маршрута по умолчанию.

Пример для нового сервера; значения документационные, замени их реальными:

```bash
awg-tool install \
  --host 203.0.113.9 \
  --user root \
  --key "$HOME/.ssh/id_ed25519" \
  --version 3.1 \
  --endpoint vpn.example.com \
  --listen-port 51820 \
  --pull
```

Для нерутового пользователя с нужным sudo добавь `--sudo`. Для agent-auth не
передавай `--key`. Для входа по паролю есть флаг `--password` без значения:
пароль спрашивается без эха; не передавай его в аргументах и shell history.
Ключ с парольной фразой: `--key ПУТЬ --key-passphrase`.

### Что делает команда

1. Соединяется по SSH (порт 22, пользователь root по умолчанию). Для
   неизвестного host key показывает отпечаток и спрашивает `[y/N]`. Сверь
   отпечаток доверенным способом перед согласием. Несовпадение это отказ, а не
   повод удалить `known_hosts` или отключить проверку.
2. Проверяет дистрибутив, `docker`, `iptables`, `ip`, `curl`, доступ к Docker,
   sudo, маршруты и IPv4 forwarding. Внешний сервис определения IP не
   вызывается: endpoint берётся из `src` маршрута. Это может дать частный адрес
   или ничего; задавай `--endpoint` явно, если нужно.
3. Для отсутствующих пакетов печатает точную команду и спрашивает `[y/N]`.
   Семейства apt/dnf/pacman/zypper/apk/xbps/emerge выбираются по ОС и `ID_LIKE`.
   NixOS и неизвестную систему не исправляет случайным менеджером пакетов.
4. Проверяет занятость UDP-порта; занятый порт это отказ с указанием владельца,
   не убийство процесса. `--listen-port` выбирает другой порт.
5. Если образа нет, без `--pull` останавливается; с `--pull` разрешено его
   скачать. Уже имеющийся образ этот флаг **не обновляет**.
6. Генерирует ключи и параметры, пишет серверную конфигурацию, пересоздаёт
   контейнер этого поколения и проверяет поднятие интерфейса.
7. Печатает endpoint, имя контейнера, полный первый клиентский `.conf` и
   `vpn://`. Сохрани оба как секреты. Это ещё не доказательство handshake
   с реальным устройством.

### Реальный контракт install

| Параметр | Текущее значение и возможности |
|---|---|
| Поколение | `--version` (по умолчанию 3.0); все флаги `gen` действуют, имя для мимикрии: `--mimic-host` |
| Контейнер | `awg1-server`, `awg15-server`, `awg2-server`, `awg3-server`, `awg31-server` по поколению; `--name` меняет |
| Образ | `vaiprog/amnezia-wg-1/15/2/3/31:latest` по поколению; `--image` переопределяет |
| Конфиг на хосте | `/etc/amnezia/awg1`, `awg15`, `awg2`, `awg3`, `awg31`: `server.conf` и `server.key` |
| Туннель | `awg0`, сервер `10.8.1.1/24`, первый клиент `10.8.1.2/32` |
| MTU | `1420`, для 3.1 `1280` (пресет версии) |
| DNS первого клиента | `1.1.1.1, 8.8.8.8`; внутренний резолвер и страницы install не разворачивает |
| AllowedIPs первого клиента | `0.0.0.0/0, ::/0`; строка IPv6 не доказывает работу IPv6 |
| Keepalive | `25` |
| Endpoint | `--endpoint HOST` **без `:PORT`**; порт берётся из `--listen-port` |
| Экспорт | Только общий stdout; `install --out` и `--json` не реализованы |

Не выдумывай `--dns`, `--allowed-ips`, `--conf-dir`, `--yes` или
`--non-interactive` для install: обработчик их не реализует, а ручной парсер
может молча проигнорировать лишний флаг.

Файлы `server.conf` и `server.key` в каталоге поколения содержат секреты:
каталог `0700`, конфигурация `0600`. Каталог монтируется read-only в
контейнер. Named volumes: `<имя>-state:/var/lib/awg` и `<имя>-log:/var/log/awg`.
Контейнер получает `AWG_CONF`, `AWG_IFACE`, `AWG_ENDPOINT`, TUN, NET_ADMIN,
IPv4 sysctl и UDP publish; host networking и `--privileged` не используются.

**Повторный install того же поколения опасен:** он перезаписывает
`server.conf`/`server.key` этого поколения и делает `docker rm -f` контейнера
без финального подтверждения и автобэкапа. Это не добавление клиента и не
безопасное обновление. Для новых устройств есть `awg-tool peer add`, для новой
обфускации `awg-tool rotate`. Разные поколения живут в разных каталогах и
контейнерах, поэтому их можно ставить на один хост, но с разными
`--listen-port`.

`install > client.conf` сохраняет смесь служебных строк, конфига и ссылки,
а не чистый импортируемый `.conf`. При выполнении агентом направляй общий
stdout в новый защищённый файл вне репозитория (`umask 077`), затем извлеки
клиентский блок средствами редактора без печати секретов. Вывод ошибочной
установки тоже считай чувствительным: в нём могут быть хвосты Docker logs.

### Подготовка и известные границы

- Нужен работающий Docker daemon: отдельного универсального `enable/start`
  после установки пакета CLI не делает. Если он недоступен, сначала исправь
  сервис штатным способом выбранной ОС.
- Установка недостающих пакетов идёт через sudo даже для root. На минимальном
  хосте без `sudo` заранее и согласованно поставь пакеты подходящим менеджером.
- Install не настраивает постоянный forwarding хоста. Проверяй forwarding и
  firewall явно; `net.ipv4.ip_forward=1` контейнера не заменяет настройки хоста.
- Для NixOS при отсутствии инструментов выводится декларативная подсказка,
  например `virtualisation.docker.enable = true;` и пакеты
  `iptables iproute2 curl`. Изменение конфигурации и rebuild выполняются
  отдельно после согласования.
- SSH реализован библиотекой, не системным `ssh`: алиасы, ProxyJump и
  IdentityFile из `~/.ssh/config` не подхватываются. Пути к ключам нужны
  раскрытые или абсолютные. Если рядом с ключом лежит `.pub`, он используется.
  Не обещай работу через bastion без отдельной настройки.
- Флага unattended нет. Нужны заранее доверенный host key, доступный способ
  входа, root/NOPASSWD либо пароль sudo и отсутствие вопросов менеджера пакетов.
- `--name`, `--image`, `--endpoint` попадают в удалённые shell-команды.
  Используй простые доверенные значения без пробелов, shell-метасимволов
  и подстановок.

## Сохранённые подключения

`awg-tool profiles` это профили **мимикрии**, не SSH-серверы. Подключения
хранит `awg-tool servers`:

```bash
awg-tool servers add home --host 203.0.113.9 --user root --key ~/.ssh/id_ed25519
awg-tool servers add box --host 192.0.2.10 --user admin --password --store-password --sudo
awg-tool servers            # список
awg-tool servers rm box     # удалить вместе с сохранённым паролем
```

Затем `--server home` в `status`, `doctor`, `logs`, `peer`, `dns`, `rotate`,
`install`, а экран серверов в интерфейсе показывает их списком. Путь к ключу
сохраняется абсолютным. Пароль сохраняется **только** с `--store-password`, в
отдельный незашифрованный `secrets.json` (это не vault и не keyring); парольная
фраза ключа не сохраняется никогда. Не сохраняй пароль без явного решения
пользователя. Install сам подключение не сохраняет.

Каталог: `$XDG_CONFIG_HOME/awg-tool`, иначе на Unix `$HOME/.config/awg-tool`;
на Windows без XDG `%APPDATA%/awg-tool`. Каталог `0700`, файлы `0600`.
Неизвестные поля в `profiles.json` отклоняются: пароль туда не вписывается.

`--server home` выбирает профиль целиком; `--user`, `--key`, `--sudo` его не
переопределяют. `--server` и `--host` вместе это ошибка. Без явной цели
единственный профиль выбирается сам, несколько требуют выбора; если профилей
нет и на этой машине работают наши контейнеры, ответ идёт локально. Для
локальных контейнеров надёжнее всегда писать `--local`.

Интерфейс подключается к профилям без пароля или с сохранённым паролем;
для остальных он подсказывает команду CLI.

## Ручной сервер через Compose

Этот путь даёт внутренний резолвер, страницы .vpn и явный выбор поколения,
MTU и маршрутов. Выполняй на подготовленном сервере из каталога `containers/`
checkout. Исходный `docker-compose.yml` это демонстрация **server + client**
с резолвером и страницами, а не готовый конфиг VPS с вашими ключами.

1. Проверь `docker version`, `docker compose version`, наличие TUN, свободный
   UDP-порт 51820 и непересекающиеся сети `10.99.0.0/24`, `172.31.99.0/24`,
   `172.29.172.0/24`.
2. Сгенерируй один блок параметров под поколение и целевой клиент.
   После сборки CLI из `containers/`:

   ```bash
   ../target/release/awg-tool gen --version 3.1 --client amneziavpn --out params.conf
   ```

   `--out` создаёт файл с правами только владельца: в блоке 3.x есть
   секретный `HeaderProtectionKey`.
3. Получи серверную пару ключей утилитой образа, не сторонним генератором.
   Пример после согласованного скачивания образа:

   ```bash
   umask 077
   docker run --rm --entrypoint awg vaiprog/amnezia-wg-31:latest genkey > server.key
   docker run --rm -i --entrypoint awg vaiprog/amnezia-wg-31:latest pubkey < server.key > server.pub
   ```

   Не выводи приватный ключ в общий журнал. Создай `server.conf` с `[Interface]`,
   этим `PrivateKey`, `Address = 10.99.0.1/24`, `ListenPort = 51820`,
   `MTU = 1280` и блоком из `params.conf`. Формат описан в
   [configuration.md](configuration.md). Для выдачи через `awg-tool peer` или
   `awg-peer` стартовый `[Peer]` не обязателен; не добавляй фиктивные ключи.
4. Укажи серверу образ нужного поколения (`vaiprog/amnezia-wg-31` для 3.1) и
   mount `./server.conf:/etc/amnezia/awg/awg0.conf:ro`. Сохрани named volumes
   (`awg-state`, `awg-log`, `awg-names`, у резолвера `awg-dns-state`,
   `awg-dns-public`), `NET_ADMIN`, TUN, sysctl, UDP publish и подключение
   сервера к DNS bridge. Другое поколение требует соответствующего образа
   **и** совместимого блока параметров.
5. Для реального VPS не запускай демонстрационный `client`: убери его из
   собственного файла или запускай только нужные сервисы. Оставь bridge-mode и
   опубликованный UDP-порт, если нет причины менять сетевую модель. Нельзя
   просто включить `network_mode: host` вместе с прежними `networks` и считать
   доступ к DNS bridge сохранённым.
6. Проверь синтаксис и запусти нужные сервисы:

   ```bash
   docker compose config --quiet
   docker compose up -d dns server status
   docker compose ps
   docker compose exec -T server awg-health
   ```

   `config --quiet` не печатает итоговый конфиг. Полный `compose config` может
   раскрыть подставленные секреты другого deployment-файла.
7. Выпусти отдельного реального клиента с нужным endpoint и маршрутами по
   [clients.md](clients.md). Выдача без `AWG_ENDPOINT` может оставить
   `SERVER_PUBLIC_IP`; маршруты по умолчанию это split tunnel, а не весь
   интернет-трафик.
8. После импорта проверь handshake, DNS и нужный трафик с устройства
   (`amiunder.vpn`, `leak.vpn`). Только после этого установка подтверждена.

Для демонстрационной пары нужны ещё полноценный `client.conf` и его ключи,
серверный `[Peer]`, совпадающие параметры и внутренний endpoint; обычное
`docker compose up -d` пытается запустить и этот клиент. Не советуй такую
команду, если подготовлен только серверный файл.

## Несколько серверов и локальная сборка образов

Несколько поколений поддерживаются отдельными контейнерами с уникальными
портами, туннельными и bridge-подсетями, именами и state/log volumes. Если
интерфейсы живут в одном host namespace, им нужны уникальные имена и routing
marks/tables (по умолчанию они берутся из listen port). `awg-tool install`
разных поколений уже разводит контейнеры и каталоги конфигов; повторный
install **одного** поколения с другим `--name` всё равно пишет в тот же каталог.

Сборка образов из исходников, из `containers/`:

```bash
./build.sh 3.1
./build.sh dns status
./build.sh
```

Последняя команда собирает все пять поколений, резолвер и страницы;
`AWG_IMAGE_PREFIX` выбирает свой префикс. Локальная сборка ничего не публикует.
Публикация в registry это отдельное действие владельца, не часть установки.
Проверки контейнерных изменений описаны в [operations.md](operations.md).
