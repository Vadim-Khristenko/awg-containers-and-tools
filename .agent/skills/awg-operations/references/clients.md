## Выбор инструмента и предварительные проверки

В текущем `awg-tool` нет `peer add`, `peer list`, `client add` или `export`.
Дополнительными peers управляет **существующая** утилита `awg-peer` внутри
контейнерных образов проекта. Источник истины — `containers/awg-peer` и
восстановление peers в `containers/entrypoint.sh`.

Все `docker ...` ниже запускаются на Docker-хосте сервера. Для SSH сначала
подключись к нужному хосту, например `ssh -i ~/.ssh/id_ed25519 root@203.0.113.9`,
и уже там выполняй команды. Для нерутового пользователя используй согласованный
способ доступа к Docker; не добавляй его автоматически в группу `docker` —
членство фактически даёт root-доступ.

До изменения:

1. Подтверди контейнер, поколение и интерфейс. Примеры ниже используют
   `awg-server`/`awg0`; имя после SSH-install может отличаться.
2. Проверь `docker exec awg-server awg-peer list`: имя должно быть новым,
   адрес — свободным. Автовыделение пригодно только для обычного IPv4 `/24`.
3. Уточни приложение/версию устройства. `awg-peer` не принимает `--client` и
   не адаптирует блок обфускации под Windows/роутер. Если существующие общие
   параметры несовместимы с новым клиентом, выбери совместимое приложение или
   согласованную миграцию всех сторон; не перегенерируй только новый файл.
4. Найди публичный endpoint. Для `AWG_ENDPOINT` это **host:port**, в отличие от
   `awg-tool install --endpoint`, которому нужен host без порта. В bridge-mode
   укажи внешний опубликованный порт, даже если внутренний `ListenPort` другой.
5. Определи full/split tunnel и DNS. DNS `172.29.172.254` работает только там,
   где реально развёрнут внутренний resolver с доступом от AWG-сервера.
6. Убедись, что `/var/lib/awg` сохранён в volume или что согласованные
   `AWG_STATE_DIR`/`AWG_PEERS_DIR` ведут к постоянному хранилищу. Без этого
   новый доступ потеряется при пересоздании контейнера.

## Выдача конфигурации

Метка содержит только `A–Z a–z 0–9 . _ -`, например `alice-phone`.
Используй простые имена с буквенным началом; не используй пути и `..`.
Создавай клиентов последовательно: утилита не блокирует конкурентное
выделение одного и того же свободного адреса.

### Полный IPv4-туннель

Следующий пример добавляет **новый** peer и сохраняет его приватный конфиг
на машине, где запущен Docker CLI. Подставь реальный endpoint; пример
предполагает, что tunnel-only DNS из Compose действительно существует.

```bash
umask 077
mkdir -p "$HOME/awg-client-configs"
chmod 700 "$HOME/awg-client-configs"
# Перед выдачей убедись, что файл с этим именем ещё не существует.
docker exec \
  -e AWG_ENDPOINT=vpn.example.com:51820 \
  -e AWG_CLIENT_DNS=172.29.172.254 \
  -e AWG_CLIENT_ALLOWED=0.0.0.0/0 \
  awg-server awg-peer add alice-phone \
  > "$HOME/awg-client-configs/alice-phone.conf"
```

Не используй `-t`/`-it` при перенаправлении: конфигурация должна попасть в
чистый stdout, диагностические события — в stderr. Проверяй код возврата.
Shell создаёт/обнуляет файл **до** запуска команды, поэтому не перенаправляй
повторную неудачную выдачу в единственную сохранённую копию. После ошибки
не считай пустой или частичный файл действующим конфигом.

При запуске на VPS файл останется на VPS. Передавай владельцу устройства
по приватному каналу или забери через SCP в защищённый локальный каталог;
не вставляй содержимое в issue, общий чат, QR-сервис или публичный pastebin.
Приватный ключ выдаётся один раз: защищённая локальная копия — обязанность
оператора, а не функция повторного экспорта `awg-peer`.

### Split-tunnel с DNS и статус-страницей

Для отдельного нового устройства `alice-laptop`:

```bash
umask 077
docker exec \
  -e AWG_ENDPOINT=vpn.example.com:51820 \
  -e AWG_CLIENT_DNS=172.29.172.254 \
  -e 'AWG_CLIENT_ALLOWED=10.99.0.0/24, 172.29.172.254/32, 172.29.172.253/32' \
  awg-server awg-peer add alice-laptop \
  > "$HOME/awg-client-configs/alice-laptop.conf"
```

Здесь сеть `10.99.0.0/24` должна совпадать с фактической сетью сервера.
`AWG_CLIENT_ALLOWED` заменяет весь список, а не дополняет default.
Для фиксированного адреса синтаксис — `awg-peer add alice-laptop 10.99.0.7`;
сначала отдельно проверь отсутствие конфликта. Не выполняй второй `add` для
уже созданной метки: это не команда редактирования.

Для Compose эквивалентная форма использует имя сервиса, не контейнера:

```bash
docker compose exec -T \
  -e AWG_ENDPOINT=vpn.example.com:51820 \
  -e AWG_CLIENT_ALLOWED=0.0.0.0/0 \
  server awg-peer add bob-tablet
```

Без перенаправления эта команда печатает секрет в терминал. В работе агента
предпочитай защищённый файл по первому примеру, не логируемый вывод.
Переменные `docker exec -e` действуют только на этот вызов; чтобы применять
настройки к будущим выдачам, задай их в `environment` сервиса и согласованно
пересоздай контейнер с сохранением state-volume.

## Хранение состояния и ограничения

`awg-peer add`:

- читает адрес `[Interface] Address` и ищет свободный хост `.2–.254` в `/24`;
- проверяет занятость через живой UAPI, включая peers из исходного `.conf`;
- создаёт client private/public key и PSK, добавляет peer через UAPI;
- сохраняет `Label`, `PublicKey`, `Address`, `PresharedKey`, `Created` в
  `/var/lib/awg/peers.d/<label>.peer`, файл `0600`, каталог `0700`;
- выводит клиентский private key только в выдаваемом `.conf`, не сохраняет его
  в peer-record и не поддерживает восстановление/повторный export;
- копирует блок обфускации из серверного **файла**, не из live-настроек UAPI;
- добавляет `PersistentKeepalive = 25`, DNS и маршруты из переменных;
- не создаёт `vpn://` и QR-код.

Default `AllowedIPs` — `<tunnel>/24, <DNS>/32`, то есть **split-tunnel**, а не
выход всего трафика в интернет. Default endpoint может остаться буквальным
`SERVER_PUBLIC_IP:51820`; такой файл сначала исправь, не отправляй клиенту.

Существенные границы текущей реализации:

1. Алгоритм автонумерации считает сеть `/24` по первым трём октетам, не по
   действительной маске. При другой маске/IPv6 не доверяй автовыдаче.
2. Явный IP не получает полноценной проверки подсети/занятости. Даже
   автовыделение проверяет точные `/32`, а не все возможные перекрытия
   `AllowedIPs`. Не назначай адрес по принципу «команда не возразила».
3. Если server address не `.1`, проверяй также конфликт с адресом самого
   сервера: перебор `.2–.254` не резервирует произвольный server address.
4. `conf_obfuscation()` в `containers/awg-peer` **не копирует
   `RandomTrailers`/`DisableCookies`**. Для 3.1 проверь эти поля отдельно;
   не обещай, что «все параметры 3.1 автоматически перенесены». Если нужны
   те же настройки, добавь поддерживаемые поля в защищённую копию клиентского
   `[Interface]` после сверки серверной политики и возможностей приложения.
5. Изменение параметров через raw UAPI без изменения серверного `.conf`
   создаёт рассинхронизацию будущей выдачи и следующего старта.
6. Runtime-добавление происходит до записи peer-record и вывода конфига.
   Если команда оборвалась, проверь `list` и наличие постоянной записи:
   не повторяй слепо `add` и не оставляй неизвестный рабочий доступ.

## Импорт и проверка устройства

1. Передай `.conf` только владельцу устройства. Импортируй в приложение,
   поддерживающее выбранное поколение AmneziaWG, не в обычный WireGuard
   без AWG-поддержки. Точные названия UI зависят от приложения и версии.
2. Убедись, что endpoint не placeholder, адрес уникален, DNS/AllowedIPs
   соответствуют задаче; содержимое секретных строк в чат не копируй.
3. Подключи устройство и инициируй трафик. На сервере проверь:

   ```bash
   docker exec awg-server awg-peer list
   ```

   Ожидается ненулевой свежий handshake именно нового публичного ключа;
   `never` до первого включения устройства нормален.
4. С клиента проверь доступ к tunnel-IP сервера и нужным ресурсам. Для
   внутреннего DNS — запрос к `172.29.172.254`; для страницы —
   `http://amiunder.vpn` при наличии DNS и маршрута `172.29.172.253/32`.
   Для full-tunnel проверь выходной IPv4 на доверенном ресурсе; заранее
   предупреди, если это сторонний сервис, получающий адрес клиента.
5. Проверь системный DNS/DoH и IPv6 отдельно. `0.0.0.0/0` не означает полный
   IPv6-туннель, а серверный health не доказывает отсутствие утечек на телефоне.

`vpn://`, выведенный после `awg-tool install`, содержит приватный конфиг:
это сжатая base64url-упаковка JSON, **не шифрование**. Самостоятельной
CLI-команды для превращения произвольного `.conf` в ссылку сейчас нет.
Не обещай её вместо поддержанного импорта `.conf`.

## Отзыв и ротация

После явного разрешения на отзыв конкретного клиента:

```bash
docker exec awg-server awg-peer list
docker exec awg-server awg-peer rm alice-phone
docker exec awg-server awg-peer list
```

`rm` принимает метку **или base64 public key**. Проверь точное совпадение
перед выполнением. У динамического peer команда удаляет live peer и
`peers.d`-record. Убедись в отсутствии публичного ключа после операции и,
если согласован перезапуск, после него тоже.

`(unlabelled)` в списке может быть peer из смонтированного серверного `.conf`.
`rm <public-key>` удалит его только из live-устройства; при запуске entrypoint
он вернётся. Для постоянного отзыва убери ровно соответствующий `[Peer]` из
постоянного серверного файла, проверь отсутствие копии в `peers.d`, затем
примени изменение в согласованное окно. Не очищай все peers или volume.

Потерянный клиентский private key не восстанавливается по публичному ключу
или PSK на сервере. Отзови старый peer, создай новый, передай новый `.conf`
и проверь handshake. Для утечки серверного private key или общего
HeaderProtectionKey нужна согласованная ротация затронутого набора сторон,
а не только переименование метки клиента.
