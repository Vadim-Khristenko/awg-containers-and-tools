## Выбор цели и обзор состояния

Для локальных контейнеров на машине с доступным Docker:

```bash
awg-tool status --local
awg-tool status --local --container auto
awg-tool doctor --local --container awg-server
awg-tool logs --local --container awg-server --lines 200
```

Имена примеров замени фактическими. `status` принимает выбор контейнера через
`--container`; `logs`/`doctor` допускают также позиционное имя.
`auto` выбирает единственный AWG-узел, исключая DNS/status sidecars;
несколько узлов требуют точного имени. Без фильтра обрабатываются найденные
контейнеры, включая sidecars. Discovery использует образ/labels, а не только
префикс имени; переименованный узел не обязательно потеряется.

Не полагайся на автоматический local/remote выбор: текущая реализация при
наличии SSH-профилей не выбирает local автоматически. `--local` явно имеет
приоритет даже над переданными remote-флагами; не смешивай их. В local режиме
`--sudo` не меняет способ запуска Docker — текущему пользователю уже нужен
согласованный доступ.

Remote-синтаксис существует, например `awg-tool status --server home` или
`awg-tool doctor --host 203.0.113.9 --key "$HOME/.ssh/id_ed25519"`, но у
текущего CLI есть известное **ограничение реализации**: в
`crates/awg-cli/src/ops.rs`, функции `survey()`, remote-ветка соединяется по
SSH, а список контейнеров получает через `local_containers()`. Пустой список
здесь не доказывает, что на VPS нет сервера; `--container` сам по себе
discovery не обходит. Для надёжного наблюдения подключись системным SSH к
целевому хосту и выполни там Docker-команды либо локальный `awg-tool --local`,
если бинарник установлен. TUI Servers использует remote discovery отдельно,
но требует подготовленного auth/known_hosts и не заменяет CLI password prompt.
Это ограничение описано по коду, не как результат проверки конкретного VPS.

`status` показывает образ, состояние, порты, uptime, интерфейс, суммарные
RX/TX и число когда-либо handshaked peers. Это не персональный online-список:
выключенный телефон может оставаться в счётчике `ever-handshaked`.
Для индивидуальных строк используй `docker exec awg-server awg-peer list`.

## Диагностика по уровням

Начни с наблюдения без перезапуска. После включения клиента инициируй трафик:
без него старый/нулевой handshake не всегда неисправность.

| Уровень | Проверка на Docker-хосте | Что она доказывает |
|---|---|---|
| Контейнер | `docker compose ps` или `docker ps -a` | Процесс запущен/остановлен, порты опубликованы |
| Интерфейс и UAPI | `docker exec awg-server awg-health` | Интерфейс поднят, UAPI отвечает; не реальный интернет |
| Peers | `docker exec awg-server awg-peer list` | Адреса, public keys, последний handshake |
| Туннельные маршруты | `docker exec awg-server ip route` и `ip rule` | Наличие маршрутов/rules в нужном namespace |
| DNS | Запрос с клиента к `172.29.172.254` | Достижимость внутреннего резолвера по клиентскому пути |
| Нужный сервис | Трафик с реального клиента | Работу конкретного маршрута/протокола, не всех путей |

`doctor` добавляет evidence/confidence, alternatives и blind spots. Сохраняй
это различие в ответе: `possible` — не подтверждённая причина. Текущий CLI/TUI
не передаёт client `.conf` в core-диагностику; флага `--client-conf` нет.
Если требуется сравнение обфускации, сравнивай известные поля приватно
доступным редактором, не проси вставить полный секретный конфиг в чат.

Характерные симптомы:

| Симптом | Следующая минимальная проверка |
|---|---|
| TUN/interface отсутствует | TUN на хосте, mount `/dev/net/tun`, `NET_ADMIN`, ошибка старта |
| Демон отклонил конфиг | Поколение образа, допустимые ключи/теги, совпадение формата; `errno` |
| `HeaderProtectionKey` не распознаётся инструментом | Не применяй старый `awg setconf`; штатный entrypoint переводит `.conf` в UAPI |
| Peer `never`, устройство ещё не включали | Сначала включить и инициировать трафик, не менять сервер |
| Нет handshake после трафика | Endpoint/UDP publish/firewall/NAT, public keys/PSK, обфускация и версия приложения |
| Handshake есть, IP-трафика нет | AllowedIPs на обеих сторонах, IPv4 forwarding, NAT, маршруты и MTU |
| IP работает, имена нет | DNS клиента, маршрут DNS `/32`, доступ сервера к resolver bridge, egress Unbound |
| DNS работает, `amiunder.vpn` нет | Маршрут `172.29.172.253/32` у split-tunnel, работа status, адрес записи DNS |
| Новые peers пропали после пересоздания | Постоянный state-volume, `AWG_PEERS_DIR`, логи восстановления |
| Удалённый peer вернулся | Наличие его `[Peer]` в постоянном `.conf` или записи `peers.d` |
| Периодические зависания крупных запросов | Path MTU/padding, не автоматическое увеличение S/J |

Нулевые host DNAT counters не доказывают отсутствие входящих пакетов:
Docker proxy может передавать их другим путём. Старый handshake (doctor
использует порог больше 300 секунд) не доказывает поломку выключенного
клиента. Не убивай посторонний процесс на занятом UDP-порту.

### Утилиты внутри клиентского контейнера

```bash
docker exec awg-client awg-under
docker exec awg-client awg-leak
```

`awg-under` пробует внутреннюю страницу из **этого** namespace; на сервере
она может быть доступна напрямую по bridge и не доказывает VPN на телефоне.
`awg-leak` проверяет resolver контейнера, DNS-пробу и default route. Поле DNS
в `.conf` само не меняет контейнерный `/etc/resolv.conf`: Docker resolver
`127.0.0.11` на full-tunnel может оставаться обходным путём.

При policy routing main table может содержать обычный default route, хотя
фактический трафик направляется через отдельную таблицу и fwmark. `awg-leak`
смотрит основной default и способен назвать это утечкой: перепроверь
`ip rule`, нужную routing table и реальный путь, не удаляй корректные rules
только ради зелёного verdict. Ни одна из утилит не проверяет автоматически
настройки DoH/IPv6/fallback всех внешних устройств.

## Логи и секреты

`awg-tool logs` выполняет redaction известных имён полей и форм ключей в core.
Предпочитай его для первичного анализа там, где local discovery работает.
Это эвристическая очистка, а не гарантия удаления произвольного секрета.
`--lines` по умолчанию 200; `--follow`/`--since` не реализованы.

Сырой `docker logs`, stdout/error `install`, произвольные config dumps и
`vpn://` эту очистку не проходят. Не выполняй `awg-uapi get` в публичный
транскрипт: UAPI возвращает private key, PSK и header-protection material.
Ответ `errno=0` не делает предшествующие строки безопасными для публикации.

Встроенный `awg-dump` собирает интерфейс, маршруты, UAPI, NAT и хвост событий.
**В текущем `containers/awg-dump.sh` фильтруются только строки
`private_key` и `preshared_key`, не `header_protection_key`.** Поэтому для 3.x
не считай dump заведомо обезличенным. Если он нужен, сохраняй локально в новый
защищённый файл, проверь/удали все секретные поля доступным редактором до
передачи; не публикуй raw dump в issue. Новый скрипт redaction не требуется.

`AWG_DUMP_REQUEST=1` пишет `/tmp/uapi-set.req` с private key. По умолчанию он
выключен; не включай без необходимости и согласования. После разрешённой
диагностики выключи режим и удали секретный артефакт согласованным способом.

Журнал событий `/var/log/awg/events.log` дублируется в stderr. Он содержит
события start/config-applied/peer-add/client-config-issued/peer-remove/stop,
не тела конфигов; ротация по 256 KiB с одной старой копией. Но labels, адреса,
public keys и история доступа остаются чувствительными метаданными.
Согласуй их удаление/маскирование перед внешней передачей.

## Обновление и откат

`awg-tool update` — **проверка**, не загрузка и не установка обновления.
Без `--server`/`--host` проверяет только GitHub-версию CLI; `update --local`
также не означает проверку всех локальных images. Remote image-check имеет
описанную выше проблему discovery. Данные берутся HTTPS-запросами с машины
CLI к GitHub/Docker Hub; сетевые ошибки и local image без RepoDigest дают
`Unknown`, а не доказательство актуальности.

Для реального обновления:

1. Определи источник deployment: Compose или `docker run` от install.
   Зафиксируй текущий image digest/ID и описание контейнера без публикации
   secrets. Плавающий `latest` не годится как единственная точка отката.
2. Согласуй окно обрыва, сделай защищённый backup конфигов и state, обеспечь
   доступ к старому образу. Обновляй патч текущего поколения; переход между
   поколениями — отдельная миграция клиентов/конфигурации.
3. Для Compose после согласования можно выполнить из deployment-каталога:

   ```bash
   docker compose pull server
   docker compose up -d server
   docker compose exec -T server awg-health
   ```

   `pull` скачивает, `up` пересоздаёт с прежними mounts/volumes. Не добавляй
   `down -v`, не перезапускай все sidecars без причины.
4. Для установки через `docker run` восстанови точные mounts/env/ports/sysctls,
   volumes и restart policy из inspect/описания deployment. Не выдавай
   универсальный `docker run` с пустым состоянием как «update»; не используй
   повторный `awg-tool install` — он меняет ключи/конфиг.
5. Проверь реального клиента, handshake/счётчики, DNS и нужный трафик. При
   отказе восстанови прежний pinned image и согласованный комплект конфигов
   со state; повтори проверки. Откат не автоматический.

## Резервное копирование и восстановление

В CLI нет `backup`/`restore`. Используй доступные оператору штатные средства
файловой системы/Docker, не добавляя проекту новые shell-обвязки.

Сохрани согласованный набор:

- фактический host `server.conf` и server private key (`/etc/amnezia/awg3`
  для install либо свои bind mounts для Compose);
- state-volume (`peers.d`, PSK, счётчик boots); при параллельном изменении
  peers резервная копия может быть несогласованной — на время копии запрети
  изменения либо согласуй остановку;
- deployment-файл/описание, image digest, ports/env/sysctls, network topology;
- нужный по политике log-volume, с учётом чувствительности истории доступа;
- клиентские `.conf`/ссылки в отдельном защищённом хранилище, если нужна
  возможность повторного импорта: сервер не хранит client private key;
- локальные SSH-профили и `known_hosts` при переносе операторского рабочего
  места; secrets store — только если пользователь решил его хранить.

Backup — секрет, включая PSK и HeaderProtectionKey. Не прикладывай архив к
контрибьюту и не складывай его в checkout. Восстанавливай с прежними правами,
тем же серверным ключом и нужными volumes; пустой новый контейнер с тем же
именем — не восстановление. Проверь peers и реальный клиент до объявления
успеха. Не удаляй оригиналы до проверенного восстановления.

## Карта исходников и проверки контрибьюта

| Путь от корня | Область |
|---|---|
| `crates/awg-cli/src/main.rs` | Команды, ручной парсер, генерация, clients/profiles |
| `crates/awg-cli/src/ops.rs` | Install, status/doctor/logs/update, выбор цели |
| `crates/awg-cli/src/remote.rs` | SSH resolution, trust и password prompts |
| `crates/awg-core/src/versions.rs` | Поколения, возможности клиентов, ограничения генератора |
| `crates/awg-core/src/deploy/` и `deploy.rs` | Рендер `.conf`, defaults, survey, подготовка и deployment |
| `crates/awg-core/src/profile.rs`, `ssh.rs` | JSON-профили, secrets store, SSH |
| `crates/awg-core/src/docker/` | Discovery, health, redaction, evidence-based diagnosis |
| `crates/awg-core/src/vpn.rs`, `update/` | Упаковка ссылки и read-only update checks |
| `containers/entrypoint.sh`, `awg-peer` | Запуск через UAPI, сеть, динамические peers |
| `containers/docker-compose.yml`, `README.md` | Пример топологии и контейнерная справка |
| `CONTRIBUTING.md`, `RU.CONTRIBUTING.MD` | Правила вклада и проверок |

Для изменений Rust штатные проверки из корня:

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

Для изменений контейнеров используй **уже имеющиеся** `containers/selftest.sh`,
`utiltest.sh`, `dnstest.sh`, `paralleltest.sh` по их документации. Это реальные
туннели/трафик, им нужны Docker/TUN/привилегии и отдельное безопасное окружение.
Не запускай их на чужом production-хосте и не объявляй пройденными по чтению
README. Изменение только справки не требует развёртывания VPN: проверь ссылки,
реальные команды безопасной части CLI и сценарии ответов агента.

Обновляй справку при изменении публичного поведения. Не закрепляй текущее
ограничение как вечный контракт: перед эксплуатацией сверь исходники. В этом
навыке нет дополнительных скриптов; команды используют существующие инструменты.
